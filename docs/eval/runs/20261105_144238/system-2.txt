## Security review — `account_service.py`

| # | Finding | Evidence | Impact | Priority | Proposed Fix | Risk |
|---|---------|----------|--------|----------|--------------|------|
| 1 | **SQL injection** — `username` interpolated into the query via f-string | `account_service.py:34` | Full DB read/write; auth bypass via `' OR '1'='1` as username | Critical `CONFIRMED` | Parameterize: `"... WHERE username = ?", (username,)` | Low |
| 2 | **Command injection** — `filename` and `user_id` interpolated into a `shell=True` command | `account_service.py:120-125` | Arbitrary command execution as the service user (`x.csv; curl …`) | Critical `CONFIRMED` | Drop `shell=True`, pass an argv list, validate `filename` against `^[A-Za-z0-9._-]+$` | Low |
| 3 | **Path traversal** — `filename` goes unvalidated into `os.path.join`; an absolute path or `../` escapes `EXPORT_DIR` | `account_service.py:119`, read at `:126` | Write outside the export dir, then read back any file the process can read (`/etc/passwd`, the DB) | Critical `CONFIRMED` | Reject separators/`..`, then assert `os.path.realpath(dest).startswith(os.path.realpath(EXPORT_DIR) + os.sep)` | Low |
| 4 | **Hardcoded secret in source** — live-looking signing key committed | `account_service.py:19` | Key disclosure to anyone with repo/source access; offline hash cracking | Critical `CONFIRMED` | Load from env/secret store; rotate the exposed key | Medium — rotation invalidates existing hashes |
| 5 | **Plaintext password written to logs** on every successful login | `account_service.py:61-63` | Credential harvesting from log files/aggregators; also a compliance violation | Critical `CONFIRMED` | Remove the `password=%s` argument entirely | Low |
| 6 | **Missing authorization (IDOR)** — `session_user_id` is accepted but never used; any session can update any account | `account_service.py:83-96` (param unused through `:100`) | Horizontal privilege escalation: change another user's email → account takeover via reset | Critical `CONFIRMED` | Enforce `session_user_id == target_user_id or actor role == admin`, as `deactivate_account` does at `:160` | Low |
| 7 | **Missing authorization (IDOR)** — same unused `session_user_id`; reads any profile, including `role` | `account_service.py:103-111` | Arbitrary user data disclosure across accounts | High `CONFIRMED` | Same ownership/admin check before the query | Low |
| 8 | **No authorization on data export** — no session context at all; `user_id` is taken on trust | `account_service.py:117-121` | Any caller can export any account's full data | High `CONFIRMED` | Add `session_user_id` and verify ownership/admin before exporting | Low — signature change, grep callers first |
| 9 | **Unsuitable password hashing** — single-pass SHA-256 with a shared static pepper, no per-user salt, no work factor | `account_service.py:72-75` | GPU cracking at billions of guesses/sec; identical passwords yield identical hashes | High `CONFIRMED` | Move to `bcrypt`/`argon2`/`scrypt` with per-user salt; rehash on next successful login | Medium — migration needed |
| 10 | **Non-constant-time hash comparison** | `account_service.py:59` | Timing side channel on digest comparison (hard to exploit, but free to fix) | Medium `CONFIRMED` | `hmac.compare_digest(...)` | Low |
| 11 | **`password_hash` leaks out of the lookup** — returned in the dict to every caller of `find_by_username` | `account_service.py:34, 36` | Hash exposure if a caller serializes the record into an API response | Medium `CONFIRMED` | Select the hash only in the credential path, or strip it before returning | Low — check callers |
| 12 | **Export failures are swallowed** — `check=False`, then the file is opened regardless | `account_service.py:124, 126` | A failed export reads a stale file from a previous run (another user's data) or raises an opaque `FileNotFoundError` | Medium `CONFIRMED` | `check=True`, write to a unique temp path, clean up after read | Low |
| 13 | **Unbounded `days` parameter** — only `limit` is capped | `account_service.py:130-134` | `days` is user-controllable; negative/huge values make the window meaningless, though `LIMIT` caps the result size | Low `CONFIRMED` | Clamp `days` to a sane range (e.g. 1–365) | Low |

Not a finding: `deactivate_account` (`:155-169`) does the ownership/admin check correctly — it's the model the other three functions should follow. The email regex at `:150` is restrictive enough (`fullmatch`, no `@`/whitespace in either part) that I found no bypass.

**Fix order:** 1, 2, 3, 5, 6 first — each is independently exploitable by an unauthenticated or low-privilege caller. 4 and 9 are coupled (rotating the key and changing the algorithm should be one migration).
