Static review of all 18 Python files. I read the code but didn't run anything, so the findings come from reading the source. This is a Flask + SQLite app.

## Findings

| # | Finding | Evidence | Impact | Priority | Proposed Fix | Status |
|---|---|---|---|---|---|---|
| 1 | **Password reset tokens can be computed by anyone.** The token is `sha256(email:hour)[:32]` with no secret in it. | `password_reset.py:22-24` | Anyone who knows a victim's email can work out a valid token for the current hour and reset the password. | P0 | Use a random token stored as a hash, single use, with an expiry. At minimum, use an HMAC with `SECRET_KEY` that also covers the current password hash. | CONFIRMED |
| 2 | **The legacy `/admin/export-users` route has no authentication.** It registers the raw `admin.export_users`, not the wrapped view. The other two legacy aliases correctly use `app.view_functions[...]`, which holds the role-checked wrapper. | `routes/__init__.py:36-41` (compare `:27`, `:33`) | Anyone on the internet can download every user's id, username, email, role and active flag. | P0 | Use `app.view_functions["admin.export_users"]`. | CONFIRMED |
| 3 | **Mass assignment in onboarding.** `build_update` is called with `user_fields()`, which includes `role` and `email`. The endpoint can also be called at any time, even after onboarding is finished. | `routes/onboarding.py:53-55`, `serializers.py:3-10` | Any logged-in user can send `POST /api/onboarding/profile {"role":"admin"}` and become admin. They can also set `email` while skipping the uniqueness check and the `email_verified=0` reset. | P0 | Use a dedicated allowlist (`username`, `display_name`, `timezone`, `locale`). Reject the call once onboarding is complete. | CONFIRMED |
| 4 | **Reversing a transfer creates money.** It subtracts `amount_cents` from the entry's account. If the entry is a debit (−X), the user gets +X back. Nothing stops the same entry being reversed again, and the counterparty is never charged. | `routes/transfer.py:74-97` | A user moves money out, then reverses their own debit entry over and over, creating money each time. | P0 | Reverse both legs of the transfer atomically. Store a transfer id and a `reversed` flag. Allow only one reversal, and only within policy. | CONFIRMED |
| 5 | **Transfers are not atomic, and the balance check races.** The balance is checked at line 46, then four separate `db.execute` calls run outside any transaction. | `routes/transfer.py:46-67` | Parallel requests can overdraw an account (double spend). A failure partway through leaves the ledger and balances out of sync. | P1 | Wrap the transfer in `db.transaction()` and use a guarded update: `UPDATE ... SET balance_cents = balance_cents - ? WHERE id = ? AND balance_cents >= ?`, then check the rowcount. | CONFIRMED |
| 6 | **Batch import paths are never validated.** Only `manifest` is validated. Each entry's `path` goes straight to the job, which does `os.path.join(IMPORT_ROOT, path)`. That accepts `../` and absolute paths. | `routes/upload.py:57-74`, `jobs/import_job.py:18` | The worker will read any file it has access to. The `status` and `rows_imported` fields reveal whether a file exists and how many lines it has. Pointing it at `/dev/zero` or a FIFO passes the `getsize` check (size 0) and hangs the worker or exhausts its memory. | P1 | Run `validate_import_path` on every entry and send `resolved` in the message, as the single-import route does. | CONFIRMED |
| 7 | **Debug error output is always on.** `DEBUG` is the string `"false"`, which Python treats as true. | `config.py:7`, `app.py:57-68` | Every unhandled exception returns the traceback, exception text (which can include SQL) and `g.user` (email, role). | P1 | `DEBUG = os.environ.get("APP_DEBUG","false").lower() in ("1","true","yes")` | CONFIRMED |
| 8 | **Any member can see every user's email.** `detailed_user` is used for the directory list and for single-user lookups. | `routes/users.py:29-35`, `:41-48` | Any logged-in user can collect every user's email, timezone and last-login time. | P2 | Use `public_user` for other users' records. | CONFIRMED |
| 9 | **Login rate limit is per username only, and failed attempts are recorded before the credentials are checked.** | `routes/session.py:46-49` | Anyone can lock any account out for 15 minutes with 10 requests. Password spraying across many usernames is not throttled. | P2 | Add per-IP limits as well. Count only failed attempts. | CONFIRMED |
| 10 | **Changing email needs no password and no proof of the new address.** | `routes/profile.py:51-73` | Someone with a hijacked session can point the account at their own email, then reset the password and keep the account permanently. | P2 | Require the current password. Send a confirmation link to the new address before switching. | CONFIRMED |
| 11 | **Reset tokens can be reused and are compared in non-constant time.** Tokens are derived, not stored, so they stay valid for the whole window even after a reset. | `password_reset.py:39-44` | Replay within the hour. Becomes minor once #1 is fixed with stored tokens. | P3 | Store single-use tokens and use `hmac.compare_digest`. | CONFIRMED |
| 12 | **No rate limit on reset requests.** | `routes/session.py:90-102` | Email flooding of any user, and filling the outbox. | P3 | Rate-limit per email and per IP. | CONFIRMED |
| 13 | **LIKE wildcards in search aren't escaped.** | `routes/users.py:76` | `q=%_` matches every user, so the 2-character minimum doesn't limit enumeration. | P3 | Escape `%` and `_` and add `ESCAPE '\'`. | CONFIRMED |
| 14 | **Homemade password hashing.** It is iterated SHA-256 rather than a standard KDF. | `auth.py:17-24` | Cheaper to crack on GPUs than bcrypt, scrypt or argon2. | P3 | Switch to argon2id or scrypt (`hashlib.scrypt` is in the standard library) and rehash on next login. | CONFIRMED |
| 15 | **Session tokens are stored in plaintext.** | `auth.py:37-39` | Anyone who can read the database can hijack every active session. | P3 | Store `sha256(token)` and look sessions up by that hash. | CONFIRMED |
| 16 | **Admin user export has no row limit.** | `routes/admin.py:40-43` | Memory and response size grow with the user count. Combined with #2, an unauthenticated caller can trigger it. | P3 | Paginate or stream the export. | CONFIRMED |
| 17 | **The audit log is never written.** It is only ever read. Deactivating a user, transfers and role changes leave no trace. | `routes/admin.py:64-76` (no INSERT anywhere) | Abuse like #3 or #4 can't be detected or investigated. | P3 | Write audit entries for actions that change privileges or move money. | CONFIRMED |
| 18 | **Imports aren't scoped per user.** Every user's paths resolve against one shared `IMPORT_ROOT`. | `validators.py:47-48` | If uploads are stored per user under that root, one user can import another user's file. | P2 | Resolve against `IMPORT_ROOT/<user_id>`. | HYPOTHESIS (depends on how uploads are stored) |
| 19 | **The worker trusts `resolved` from the queue message.** | `jobs/import_job.py:15-17` | If the real queue (Redis, per `config.py:15`) can be reached without authentication, an attacker can publish messages with any path and any `user_id`. | P2 | Re-validate the path in the worker and require queue authentication. | HYPOTHESIS (the queue here is an in-memory stub) |

## Chains

- **Chain: #2 + #1 → unauthenticated takeover of any account, including admins.** #2 gives every admin's email with no login. #1 turns an email into a valid reset token. That makes it two HTTP requests from the internet to admin access. P0.
- **Chain: #8 + #1 → any member takes over any account.** This is the same attack as above without the legacy route: any logged-in user gets the emails from `/api/users`. Fixing #2 alone does not close it.
- **Chain: #3 → admin → #2/#16/#17.** A normal user makes themselves admin, exports everyone, deactivates other admins, and leaves no audit trail.
- **Chain: #4 + #5 + #17 → money creation that can't be traced.** Money can be minted repeatedly, and nothing records who did it.
- **Chain: #13 + #9 → lock out every user.** The `%` search lists all usernames (admins included), and 10 requests per account locks each one out.
- **Chain: #7 + #6.** A batch entry that is a dict without a `path`, or a non-string, crashes the request. In the current code that 500 response contains a traceback and the caller's user record.

Separately, there's a non-security bug: `verify_token` never accepts the previous window. For that window, `now - window*3600` is always more than 3600, so a token issued late in an hour expires within minutes (`password_reset.py:39-41`).

**Fix first:** #1, #2, #3 and #4. Each is a P0 that is exploitable on its own, and #1 and #2 together need no credentials at all.
