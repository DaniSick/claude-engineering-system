## Security Audit Report — `ledger` application

### Summary

The codebase has **five critical vulnerabilities** that could each independently cause account takeover, privilege escalation, or financial fraud. The most severe is a password reset token with no secret component — anyone who knows a victim's email and the approximate time of the reset request can compute the token. A close second is a privilege escalation through the onboarding flow where any authenticated user can set their own `role` to `"admin"`. The transfer system has a race condition and an incomplete reversal that together can be used to synthesize money. All findings are confirmed by direct code tracing.

### Findings (ordered by severity)

| # | Vulnerability | File:Line | CWE | Severity | Status | Fix |
|---|--------------|-----------|-----|----------|--------|-----|
| 1 | Password reset token has no secret — derived purely from email + time window, fully reproducible by an attacker | `password_reset.py:23` | CWE-640 | **Critical** | CONFIRMED | HMAC the material with `config.SECRET_KEY`; use `secrets.token_urlsafe()` stored in DB instead |
| 2 | Privilege escalation via onboarding — `user_fields()` includes `"role"`, any user can POST `{"role":"admin"}` to `/api/onboarding/profile` | `onboarding.py:54`, `serializers.py:6` | CWE-269 | **Critical** | CONFIRMED | Remove `"role"` from `USER_FIELDS` / use a separate allowlist that excludes `role` and `email` for onboarding |
| 3 | Unauthenticated admin export — legacy `/admin/export-users` registers `admin.export_users` directly, bypassing `_protected()` and its `require_role("admin")` guard | `routes/__init__.py:38-41` | CWE-862 | **Critical** | CONFIRMED | Wrap with `require_role("admin")` at registration, same as the other two legacy routes |
| 4 | Race condition / double-spend in transfers — balance check (`source["balance_cents"] < amount`) and both UPDATE statements are outside any transaction; with SQLite autocommit two concurrent requests can both pass the check and both debit, producing a negative balance | `transfer.py:46-67`, `db.py:22` | CWE-362 | **Critical** | CONFIRMED | Wrap the entire check+debit+credit+ledger block in `with db.transaction():`; use an atomic conditional `UPDATE … WHERE balance_cents >= ?` and check rowcount |
| 5 | `reverse_transfer` only reverses one ledger entry — a user can recover their debit without the recipient losing the credit, effectively creating money | `transfer.py:72-97` | CWE-840 | **Critical** | CONFIRMED | Reversal must look up and reverse both the source debit and destination credit entries in one transaction; or restrict reversals to admin only |
| 6 | `DEBUG` always truthy — `config.DEBUG` is the string `"false"` (a non-empty string, truthy in Python), so the debug error handler in `app.py` returns full tracebacks, exception types, and the `g.user` object on every 500 error | `config.py:7`, `app.py:57-68` | CWE-209 | **High** | CONFIRMED | `DEBUG = os.environ.get("APP_DEBUG","").lower() in ("1","true","yes")` |
| 7 | Batch import paths not validated — `create_batch_import` validates only the manifest path; each entry's `path` is stored and queued unvalidated; the job worker falls back to `os.path.join(IMPORT_ROOT, path)`, which an absolute path like `/etc/passwd` overrides entirely | `upload.py:64-75`, `import_job.py:17-18` | CWE-22 | **High** | CONFIRMED | Call `validate_import_path(path)` for every entry in the loop; store `resolved` in the queue message |
| 8 | Non-constant-time token comparison — `verify_token` compares reset tokens with `==` instead of `hmac.compare_digest()`, enabling timing-based token enumeration | `password_reset.py:42` | CWE-208 | **Medium** | CONFIRMED | Replace `token == _derive(email, window)` with `hmac.compare_digest(token, _derive(email, window))` |
| 9 | Account-lockout DoS — rate limiting keyed only on `username`, not IP; any unauthenticated actor can lock out any known account by sending 10 login requests | `routes/session.py:46-47` | CWE-307 | **Medium** | CONFIRMED | Key the rate limit on both username AND source IP; consider exponential backoff rather than hard lockout |
| 10 | No rate limiting on password-reset request — `/api/session/password-reset/request` has no throttle, enabling email flood against any address | `routes/session.py:90-102` | CWE-770 | **Medium** | CONFIRMED | Apply a per-IP and per-email rate limit identical in structure to the login rate limit |
| 11 | Reflected attacker-controlled header in admin response — `export_users` echoes `X-Request-Time` from the HTTP request directly into the JSON response body without validation | `routes/admin.py:46` | CWE-116 | **Low** | CONFIRMED | Use `datetime.utcnow().isoformat()` server-side; never reflect request headers into responses |
| 12 | Custom password hash construction — `hash_password` iterates raw SHA-256 (not HMAC-SHA-256), which is not PBKDF2 and lacks a pepper; GPU-amenable compared to bcrypt/argon2id | `auth.py:17-24` | CWE-916 | **Low** | CONFIRMED | Replace with `argon2.PasswordHasher()` from the `argon2-cffi` library |
| 13 | Missing `Strict-Transport-Security` header — the security-headers hook sets four headers but omits HSTS | `app.py:33-41` | CWE-523 | **Low** | CONFIRMED | Add `Strict-Transport-Security: max-age=63072000; includeSubDomains` |

### Residual risk

- **Dependencies**: no `requirements.txt` or `pyproject.toml` was present in the target; known CVEs in Flask, Werkzeug, or any Redis/SQLite wrapper could not be assessed. Run `pip-audit` or `safety check` against the installed environment.
- **Queue consumer authentication**: `queue_client.py` stores messages in a process-local list (`_pending`). The actual Redis integration (how messages are consumed from the queue) is not in scope here — the job worker's trust model for messages off the queue is unreviewed.
- **Email verification flow**: `change_email` sets `email_verified = 0` but no verification-sending logic is visible; the security of that flow is unreviewed.
- **Dynamic testing not performed**: timing-attack exploitability of finding #8 and concurrent-request exploitability of finding #4 require live testing to quantify precisely.

The security-auth specialist just landed and confirms all auth-related findings exactly as reported. One additional **Low** finding the specialist surfaced that I didn't include above:

**#14 — Reset token stored in plaintext in `outbox` table**
`routes/session.py:123-128` | CWE-312 | Low | CONFIRMED

`_enqueue_reset_email` stores the raw reset token as the `payload` column in the `outbox` table. If that table is read by any secondary access path (backup exposure, secondary SQL injection, insider), all queued tokens are valid for up to an hour. Fix: derive the token at send-time rather than storing it, or store only a hash.
