## Security Audit — `/tmp/tmp.v3vXLCQWDK/target`

### Summary

The codebase is a Flask-based financial ledger API with multi-user accounts, money transfers, file imports, and password-reset flows. The overall risk level is **critical**: four independent vulnerabilities can each achieve full financial integrity violation or account takeover without chaining, and two compound chains amplify the impact further. The most urgent finding is a mass-assignment flaw that lets any authenticated user self-promote to admin. Close seconds are three distinct flaws in the transfer/reversal flow that allow unlimited money creation. The password-reset token system is also fundamentally broken, permitting offline token forgery for any account whose email is known.

### Compound Attack Vectors

| Chain | Findings | Combined Severity | Conditions |
|---|---|---|---|
| **Self-promote then print money** | #1 → #4 | CRITICAL | Single authenticated account. POST `{"role":"admin"}` to `/api/onboarding/profile` → become admin. Initiate any transfer. POST `/api/transfers/<debit_entry_id>/reverse` repeatedly → balance grows without bound. No budget or account required beyond the initial login. |
| **Race + single-leg reversal = double funds** | #2 + #3 | CRITICAL | Two concurrent HTTP requests, one session. Race two simultaneous transfers from the same source to pass the balance check twice (Finding #2). Reverse the debit entry of one transfer (Finding #3). Net: source recovers its money; destination holds credits from both transfers. |
| **Offline token forge → account takeover → escalate** | #7 + #1 | CRITICAL | Requires knowing any registered user's email. Compute reset token offline → reset their password → log in as that user → escalate to admin via Finding #1. No interaction with the target account required. |

### Residual Risk

- **Dependencies**: no package manifest present; CVE exposure in Flask, SQLite drivers, and any unpinned libraries not assessed. Run `pip audit` against a resolved lockfile.
- **CSRF**: `SameSite=Lax` protects simple cases but does not cover all cross-site scenarios (e.g., top-level navigations or same-site subdomain attacks). A CSRF token would fully close this.
- **No password-reset rate limit**: the endpoint at `POST /api/session/password-reset/request` is unbounded; an attacker can flood reset emails for any address.
- **Dynamic testing not performed**: race condition in Finding #2 confirmed by static analysis; actual exploitability under SQLite's default locking may vary by concurrency model; verify under load.
