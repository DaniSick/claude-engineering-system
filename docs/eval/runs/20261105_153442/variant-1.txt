I read all 18 Python files (a Flask and SQLite app) and found 4 critical issues: any visitor can download the full user list, any user can make themselves admin, anyone who knows an email can reset that account's password, and users can create money from nothing. Each finding below was confirmed by reading the code, except where marked HYPOTHESIS. I didn't run anything to confirm them.

## Findings

| # | Finding | Evidence (file:line) | Impact | Priority | Proposed Fix | Risk of fix |
|---|---|---|---|---|---|---|
| 1 | **Anyone can export the full user list without logging in.** The old `/admin/export-users` route points at the raw `admin.export_users` function. It skips the `require_role("admin")` wrapper that the other two old routes get via `app.view_functions[...]`. | `routes/__init__.py:36-41`, `routes/admin.py:39-50` | Anyone on the internet gets every user's id, username, email, role and active flag. The query has no row limit, so repeated calls can also slow the server. | **P0** | Use `app.view_functions["admin.export_users"]` there, as the other two old routes do. | Low |
| 2 | **Any user can make themselves admin.** The onboarding profile step accepts any field in `serializers.user_fields()`, which includes `role` and `email`. | `routes/onboarding.py:53-63`, `serializers.py:3-10` | Any logged-in user can send `POST /api/onboarding/profile {"role":"admin"}` and become admin. The same request can set `email` with no uniqueness check, no verification, and without resetting `email_verified`. The endpoint works again even after onboarding is done. | **P0** | Pass a narrow allowlist instead, e.g. `{"username","display_name","timezone","locale"}`. | Low |
| 3 | **Password reset codes can be computed by anyone.** The token is `sha256(f"{email}:{hour}")[:32]`, with no secret key, nothing stored, and no single-use check. | `password_reset.py:22-24`, `:32`, `:42` | Anyone who knows an email can compute a valid reset code and take over that account. At minimum, sign with an HMAC keyed by `SECRET_KEY` and include the password hash so the code dies after use. | Medium (pending reset links become invalid) |

The worker should check the path again rather than trust `resolved` (`import_job.py:15-17`). Limit each user to their own folder. | Low |
| 7 | **Debug mode is always on.** `DEBUG` is read as a string, and the default `"false"` counts as true. | `config.py:7`, `app.py:57-68` | Every server error sends the user the full traceback, the error message (SQL, file paths) and the current user's details. | 10 | **Changing email doesn't require the password, and the new address is never verified.** | `routes/profile.py:51-73`, `password_reset.py:27-32` | Someone with a stolen session can change the email to their own, request a reset, and keep the account permanently. | **P2** | Ask for the current password, verify the new address before switching, and notify the old one. | Low |
| 11 | Reset requests take longer when the email exists. | `routes/session.py:98-100`, `password_reset.py:29` | Response time may show whether an email is registered (HYPOTHESIS, not measured). | P3 | Queue the work so both cases take the same time. | Low |
| 12 | Reset tokens are stored in plain text in the `outbox` table. | `routes/session.py:124-127` | Anyone who can read the database can reset passwords. | P3 | Keep the token out of the stored message, or delete it once sent. | Low |
| 13 | Session tokens are stored in plain text. | `auth.py:37-40`, `:47-49` | A leaked database or backup lets someone log in as any user. | P3 | Store `sha256(token)` and look sessions up by that. | Medium (logs everyone out) |
| 14 | Passwords use a home-made hash (SHA-256 repeated 120k times). | `auth.py:17-24` | Easier to crack on GPUs than bcrypt, scrypt or argon2. | P3 | Use `hashlib.scrypt` or argon2, and re-hash on next login. | Medium |

## Combined attacks

- **#1 + #3: anyone can take over an admin account without logging in.** `GET /admin/export-users` gives the attacker the admin emails and roles. They compute `sha256(f"{email}:{int(time.time())//3600}")[:32]` and call `/api/session/password-reset/confirm`. Combined severity: **P0**.
- **#8 + #3: any logged-in user can take over any account.** This still works after #1 is fixed: the member directory provides the emails and #3 provides the codes. **P0**
- **#7 + #6 and other errors: debug output reveals server internals.** The always-on debug mode shows tracebacks with file paths and the import folder layout, which makes building the #6 file paths easier. **P1**
- **#8 or #17 + #9: anyone can lock out all users.** Get every username, send 10 bad logins each, repeat every 15 minutes. Admins can be locked out of their own consoles during an incident. **P1**
- **#2 + #15: undetected privilege escalation.** A user who makes themselves admin can deactivate the real admins (`/api/admin/users/<id>/deactivate`), and no audit entry is written. **P0**
- **#5 + #4: draining money quickly.** Fire transfers in parallel to overdraw an account, then reverse the debit entries to restore the balance and repeat. **P0**

## Fix first

Fix #1, #2, #3 and #4 first: each is a single exploitable bug and each fix is small, except #4, which needs a schema change. Then fix #5 to #7.

I haven't changed any code. Once fixes are written, the diffs for #1, #2, #3 and #4 should get a reviewer check before commit, since they touch login, password reset, permissions and the database schema.
