**account_service.py — security review** (single file, read in full; findings verified against the code shown)

| # | Finding | Evidence | Impact | Priority | Proposed Fix | Risk |
|---|---------|----------|--------|----------|--------------|------|
| 1 | **SQL injection** — `username` interpolated into the query string via f-string | `account_service.py:34` | Full auth bypass (`' OR '1'='1`) and arbitrary read/write of the `users` table | CRITICAL `CONFIRMED` | Parameterize: `"... WHERE username = ?", (username,)` | Low — mechanical, same shape as `find_by_id` |
| 2 | **Command injection + path traversal** — unsanitized `filename` and `user_id` concatenated into a `shell=True` command | `account_service.py:119-121` | `filename="x; curl attacker/$(cat /etc/passwd)"` executes arbitrary shell as the service user; `../../etc/...` writes outside `EXPORT_DIR` | CRITICAL `CONFIRMED` | Drop `shell=True`, pass an argv list; validate `filename` against `[A-Za-z0-9._-]+` and assert `os.path.realpath(destination).startswith(EXPORT_DIR)` | Low |
| 3 | **Hardcoded secret in source** — live-looking signing key committed | `account_service.py:19` | Anyone with repo/source access can recompute every password hash offline; key rotation requires a code deploy | CRITICAL `CONFIRMED` | Load from env/secret manager, fail closed if absent; rotate the key — treat the current one as compromised | Medium — rotation invalidates existing hashes, needs a migration plan |
| 4 | **Plaintext password written to logs** on every successful login | `account_service.py:61-63` | Credentials land in log files, log shipping, and any aggregator; mass credential exposure from read-only log access | CRITICAL `CONFIRMED` | Remove the `password=%s` argument entirely | Low |
| 5 | **Missing authorization — `update_profile`** accepts `session_user_id` but never compares it to `target_user_id` | `account_service.py:83-98` | Any authenticated user can rewrite any other account's email → account takeover via password reset | CRITICAL `CONFIRMED` | Mirror the `deactivate_account` check: allow if `session_user_id == target_user_id` or actor role is `admin` | Low |
| 6 | **Missing authorization — `get_profile`** likewise ignores `session_user_id` | `account_service.py:103-112` | Any authenticated user can read any account's email and role (IDOR, enumerable by integer id) | HIGH `CONFIRMED` | Same ownership/admin check as #5 | Low |
| 7 | **Weak password hashing** — single unsalted SHA-256, with the pepper from #3 | `account_service.py:72-75` | GPU-crackable at billions of guesses/sec; no per-user salt means identical passwords produce identical hashes | HIGH `CONFIRMED` | Switch to `bcrypt`/`argon2id` with per-user salt; rehash on next successful login | Medium — needs a dual-verify migration path |
| 8 | **Non-constant-time hash comparison** | `account_service.py:59` | Timing side channel on hash comparison; low practical yield here but free to fix | LOW `CONFIRMED` | `hmac.compare_digest(...)` | Low |
| 9 | **`password_hash` returned to all callers** of `find_by_username` | `account_service.py:34` (select list), used at `:55` | Hash leaks into any caller that serializes the dict into an API response | MEDIUM `HYPOTHESIS` — depends on callers outside this file; `grep` for `find_by_username` before changing the shape | Drop `password_hash` from the public select; add a private `_credentials_for(username)` for the auth path | Medium — public signature change, caller sweep required |
| 10 | **Unvalidated `days` parameter** — only `limit` is clamped | `account_service.py:130-134` | `days` unbounded (and negative values accepted); a large value returns the entire user table within the 1000-row cap — resource/enumeration concern rather than a leak | LOW `CONFIRMED` | Clamp `days` to a sane range (e.g. `1..365`) | Low |

Two notes outside the security scope: `datetime.utcnow()` (`:64, :80, :134`) is deprecated and returns a naive datetime — `session_expired` silently raises if `issued_at` is timezone-aware; and `update_profile` returns `True` without checking that a row actually matched, so updating a non-existent id reports success.
