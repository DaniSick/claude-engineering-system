## Security review — Flask ledger app (18 files, ~1,280 LOC)

| # | Finding | Evidence | Impact | Priority | Proposed fix |
|---|---------|----------|--------|----------|--------------|
| 1 | **Privilege escalation via onboarding mass-assignment.** `complete_profile_step` passes `serializers.user_fields()` as the writable allowlist; `USER_FIELDS` includes `role` (and `email`). Any authenticated user can `POST /api/onboarding/profile {"role":"admin"}` and become admin. | `routes/onboarding.py:53-63`, allowlist at `serializers.py:3-10` | Full admin takeover from any account | **CRITICAL** | Use `serializers.WRITABLE_BY_OWNER` (plus `username`), never `USER_FIELDS`, for owner-driven writes |
| 2 | **Unauthenticated admin user export.** The legacy alias registers the bare module function `admin.export_users`. `_protected` wraps the view *at registration* (`require_role("admin")(view)`) without rebinding the module global, so the raw function has no role check. The other two aliases correctly pull the wrapped version from `app.view_functions`. | `routes/__init__.py:36-41` vs `:24-35`; `routes/admin.py:18-21,39-50` | Anonymous `GET /admin/export-users` dumps every user's email, role, active flag | **CRITICAL** | Register via `app.view_functions["admin.export_users"]` like the sibling aliases |
| 3 | **Password reset tokens are unkeyed and predictable.** `_derive` = `sha256("{email}:{window}")[:32]` — no secret, no randomness. Anyone who knows a victim's email computes the valid token offline. | `password_reset.py:22-24`, consumed at `:35-44`, `routes/session.py:105-120` | Account takeover for any user, no interaction needed | **CRITICAL** | Store random `secrets.token_urlsafe(32)` tokens hashed in DB with expiry + single use; if staying stateless, HMAC with `config.SECRET_KEY` |
| 4 | **Path traversal → arbitrary file read in batch import.** `create_batch_import` validates only `manifest`; each entry's `path` is queued unvalidated and without a `resolved` key, so the worker falls back to `os.path.join(IMPORT_ROOT, path)`. An absolute path discards the root entirely; `../` also escapes. File contents are inserted into `contacts` and readable back by the attacker. | `routes/upload.py:57-74` (no per-entry validation), `jobs/import_job.py:14-18` | Read any file the worker can reach (`/etc/passwd`, DB file, env dumps) and exfiltrate it | **CRITICAL** | Run `validate_import_path` on every entry and publish `resolved`; make `_resolve` require `resolved` rather than re-joining |
| 5 | **Replayable reversal mints money.** `reverse_transfer` has no already-reversed guard and no sign check. Reversing your own debit entry (`amount_cents = -X`) subtracts a negative, i.e. **credits** `+X`, and the reversal row it writes (`+X`) is itself reversible. Repeat for unbounded balance. | `routes/transfer.py:72-97`, esp. `:88-96` | Arbitrary balance inflation by any authenticated user | **CRITICAL** | Add a `reversed_at`/`reverses_id` column enforced unique, reject reversing a reversal, and reverse both legs of the original transfer |
| 6 | **Transfer is not atomic — TOCTOU double-spend.** The balance check and the four writes run through `db.execute` on a connection with `isolation_level=None` (autocommit); no `db.transaction()`. Concurrent requests both pass the `insufficient funds` check, and a mid-sequence failure leaves money debited but not credited. | `routes/transfer.py:46-67`; autocommit set at `db.py:22`; the correct pattern is used at `transfer.py:87` | Overdraft via race; inconsistent ledger on partial failure | **HIGH** | Wrap the whole operation in `with db.transaction()` (which issues `BEGIN IMMEDIATE`) and re-check the balance inside it, or use a conditional `UPDATE ... WHERE balance_cents >= ?` |
| 7 | **Debug tracebacks always returned in production.** `DEBUG` is the *string* `"false"` by default, which is truthy, so the `if config.DEBUG` branch always fires. | `config.py:7`, consumed at `app.py:57-68` | Every 500 leaks the stack trace, exception text, and the authenticated user object to the client | **HIGH** | `DEBUG = os.environ.get("APP_DEBUG","false").lower() in ("1","true","yes")` |
| 8 | **Non-standard password KDF.** `hash_password` iterates `sha256(digest.digest())` 120k times, folding only the 32-byte digest each round — a plain hash chain, no HMAC, GPU-friendly, and not a vetted KDF. | `auth.py:17-24` | Materially cheaper offline cracking than a real KDF if the user table leaks | **MEDIUM** | Use `hashlib.scrypt`, `argon2`, or at minimum `hashlib.pbkdf2_hmac` |
| 9 | **Login throttle keyed only on username.** `_recent_attempts` counts per identifier with no IP dimension, and attempts are never cleared on success. | `routes/session.py:20-49` | Attacker locks any account out with 10 bad guesses; password spraying across many usernames is unthrottled | **MEDIUM** | Add an IP-keyed counter, clear attempts on successful login, prefer backoff over hard lockout |
| 10 | **Import status leaks internals.** `get_import` returns the raw row including `user_id` and the server-side `path`; unlike every other endpoint it uses no serializer. | `routes/upload.py:84-93` | Minor server path / ID disclosure | **LOW** | Return a serialized subset |
| 11 | **Latent SQL injection pattern.** `build_update` interpolates column names into SQL with an f-string. Safe today only because both callers pass fixed allowlists — exactly the invariant finding #1 already broke. | `serializers.py:61-66`, used at `routes/profile.py:31`, `routes/onboarding.py:53` | No exploit today; one bad caller becomes injection | **LOW** | Assert `fields <= KNOWN_COLUMNS` inside `build_update` |
| 12 | **Import worker loads whole file before truncating.** `_read_rows` reads everything into memory, `MAX_ROWS` slices afterwards; `os.path.getsize` is also a TOCTOU check against the later `open`. | `jobs/import_job.py:30-38`, `:65-72` | Worker memory exhaustion within the 20 MB cap | **LOW** | Stream rows and stop at `MAX_ROWS`; check size on the open handle via `os.fstat` |

All findings are `CONFIRMED` by reading the code, with these caveats: #4 and #7 depend on standard Python semantics (`os.path.join` discarding the prefix on an absolute second argument; a non-empty string being truthy) that I was unable to re-run here, and #6's race is confirmed by inspection, not reproduced under load.

Two things worth noting beyond the table: the codebase has **no CSRF protection**, which is currently covered only by `samesite="Lax"` plus JSON-only endpoints — acceptable but fragile if a form-encoded or GET-based state change is ever added. And `routes/admin.py`'s module docstring asserts that every view goes through `_protected`; that claim is true inside `admin.py` but is silently defeated by the legacy alias in #2, which is what makes that bug easy to miss on review.

The sharpest cluster is #1, #2, and #3 — three independent paths to full account or admin compromise. I'd fix those first; each is a few lines.
